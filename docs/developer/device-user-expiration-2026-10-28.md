# Independent device-user expiration

28 October 2026. The operator authorized a controlled physical pilot on one named enrolled user. Its identifiers, baseline and command IDs remain in private operational records. This document describes source behavior and software checks; physical mode/count qualification is ongoing.

## Separate controls

Device users has two independent row actions: Daily time periods and Expiration rule. The daily-period action manages group/personal schedule references only. Expiration has four explicit modes: No expiration, Dates only, Entry limit only, and Dates and entry limit. Employee joining/end dates and payroll shifts remain separate application fields and are never written by these actions.

Dates require a start and end calendar date. Entry limits require a fresh explicit allowance of 1–65535; the form does not prefill an observed remaining count as a new allowance. No expiration requires neither input. Entry-limit command candidates explicitly clear inactive date fields. The No expiration command uses the supplied eBio implementation's default date range alongside the native mode; it does not write a remaining count. The qualified date-only command omits the count field; clearing a pre-existing count restriction with that command is not yet qualified. No command sends group, period, identity, privilege, card or biometric fields. Limits are written once through the encrypted command outbox, never replenished per punch. Repeated submission with the same UUID remains idempotent.

## Protocol candidate and evidence boundaries

The manufacturer-authored standalone SDK manual documents Expires modes 0/1/2/3 for none/dates/count/both. This is a native SDK contract, not independent qualification of PUSH behavior. Dates only uses the vendor DATA USER form with Expires=1, StartDatetime and EndDatetime and no count field, after a physically confirmed before-start rejection. No expiration uses DATA USER with Expires=0, StartDatetime=2000-01-01 and EndDatetime=2037-12-31, following the supplied eBio builder's default dates. Entry and combined modes currently send Expires, StartDatetime, EndDatetime and the observed PULL spelling VaildCount in an access-only USERINFO update; their count semantics still require physical qualification. Old queued mode=period requests remain accepted as date-only requests.

A known native No expiration setting can coexist with invalid-time-period rejection. Establish a permitted daily-period window and correct terminal clock before attributing a rejection to expiration. Do not change a shared group as a side effect of an individual expiration test. In particular, an empty group/period inventory response is not proof that a slot is unused.

A dependent PIN-specific read follows acknowledgement. Synced requires the returned mode and all active date/count fields to match; missing mode/count yields Verify on terminal, rather than treating stored dates or command acknowledgement as proof. The native device may omit mode/count in USERINFO. Requested allowances must not be displayed as reported remaining entries.

## Physical pilot sequence

Record the native mode, remaining count, dates, group/personal selection, daily hours and device clock. Obtain an accepted punch in a known permitted daily window first. Then isolate No expiration, date-only in-range and before-start behavior, switching back to None, count-only with one spaced same-method attempt and native remaining count after each attempt, and combined mode. Wait for operator evidence between scenarios; do not queue all scenarios at once.

Before exhausting an allowance or using a past end date, check the terminal’s expired-user handling policy. Some firmware offers retention, attendance clearing or user deletion. Keep original credentials and raw server punches intact; use an explicit test plan before a potentially destructive expiry policy is triggered. No arbitrary delay or automatic quota refill is an enforcement fix.

Source references: manufacturer-authored Standalone SDK manual, SetUserValidDate/GetUserValidDate; [SDK manual mirror](https://usermanual.wiki/Document/ManualSDKVersaoZkTeco.61245417.pdf). See the October 24 Magnum investigation for earlier date enforcement, separate daily-period evidence and the unqualified count probe. This source revision expands the earlier disabled draft for the explicitly authorized physical pilot; it does not turn those earlier observations into completed acceptance evidence.

## Rollout

Keep Laravel on work and gateway on main. Back up and coordinate both runtimes because the old gateway rejects the new modes. Expiration uses its own optional DEVICE_USER_EXPIRATION_ENABLED emergency switch and existing exact firmware/binding checks, independent from DEVICE_ACCESS_GROUPS_ENABLED. No schema migration is needed. Rebuild the gateway, update Laravel source/caches and restart affected workers before issuing a pilot command. Do not change production environment files or encryption keys as part of this update.

## eSSL compatibility investigation, 29 October

Physical testing of the modern update stored the requested future dates but left the terminal's native rule at None and allowed verification. A subsequent operator-selected date rule allowed verification, but fresh readback showed both dates were today; that attempt did not test rejection outside the date range. These results do not establish a firmware defect; terminal-wide expiration enforcement and expired-user handling must be inspected separately.

Static IL inspection of the supplied eBioServerLibrary.dll DeviceManagement.GetDeviceCommands and eTimeTrackLite App_global.asax.dll ExecuteDeviceCommands_AddUser confirms the vendor date-only command uses DATA USER, Expires=1, StartDatetime and EndDatetime, with no count field. The internal dialect=essl_dates comparison reproduced that access-only command. The terminal acknowledged it, readback confirmed the future dates and unchanged Grp/TZ, and the operator reported Invalid user before the start date. Dates-only now uses that vendor form by default; the explicit compatibility parameter remains accepted for durable command history. This qualifies before-start enforcement on the exact tested profile, but not inclusive end-date behavior or removal of a pre-existing count restriction. No identity, privilege, group, schedule or credential fields are included.

The operator reported the device-wide expired-user action as the first option, retaining the user and recording punches. It was not changed during the comparison. No delete-user policy was enabled. Identifiers and command evidence remain in a private operational record.

## Native None reset correction

The first reset was acknowledged and returned zero dates, but the operator then reported the terminal still used the date rule with today's dates. That is not a verified No expiration reset. Static IL in eTimeTrackLite App_global.asax.dll ExecuteDeviceCommands_AddUser branches on rule 0 and appends Expires=0 alone to DATA USER; it does not append date or count fields in that branch. That mode-only form was tried next, but the operator subsequently reported a remaining count of 2 after selecting an entry limit. Its acknowledgement does not establish that count mode was disabled.

Reinspection of the supplied eBioServerLibrary.dll DeviceManagement.GetDeviceCommands found a different None branch: DATA USER with Expires=0 and both StartDatetime and EndDatetime. The builder uses 2000-01-01 and 2037-12-31 as fallback dates and selects Expires=0 for the default end date. The gateway reset now includes those nonzero defaults without copying the vendor's identity/card/password/group fields. Zero dates and a zero count are deliberately omitted. The encrypted command-queue regression test covers an entry-limited command followed by this reset, idempotent submission and no resend after acknowledgement. This is software verification; native mode confirmation and a physical punch remain required. A retained inactive counter or broad returned date range alone is not proof of the selected mode or unrestricted access.

The eBio-default reset was deployed on 29 October after the Go suite, isolated PostgreSQL race tests, vet and build passed. Magnum acknowledged the targeted reset and returned StartDatetime=20000101, EndDatetime=20371231 with unchanged group and daily-period reference. It still omitted Expires and the remaining counter. The application therefore continues to show Verify on terminal; the returned range proves date delivery, not native No expiration mode or physical enforcement. The operator subsequently confirmed that the terminal still selected Entries with a remaining count of 2. This reset failed physical mode acceptance; the returned default dates and Return=0 must not be presented as a successful removal of the count rule. No later scoped write restored the limit in the inspected command history. Further reset variants are paused pending a native mode/count read or a verified vendor command trace. The eBio builder includes identity and access fields in its full user update; reproducing that complete command safely requires a fresh complete record and preservation of credentials, rather than filling omitted fields with defaults.

## Explicit easyWDMS full-record comparison

Static inspection of easyWDMS 10.2.6's `zk_get_emp_cmd_ex` confirms a full `DATA USER` record with `Expires=0` when both validity dates are empty. Its date-limited path uses `Expires=1` with `YYYY-MM-DDT00:00:00` and `YYYY-MM-DDT23:59:59`. This function does not implement entry-count modes. Neither its source nor an acknowledgement qualifies removing Magnum's Entries mode.

The explicitly requested comparison adds internal dialects `wdms_modern` (DATA UPDATE USERINFO) and `wdms_legacy` (DATA USER), for mode None only. A source event UUID must identify an authenticated targeted read for the same PIN, serial and binding, no older than two minutes. The gateway preserves the exact reported Name, Pri, Passwd, Card, Grp, TZ, Verify and optional ViceCard, including intentional empty credentials. Missing fields, duplicate records/keys, control characters, a mismatched read or stale evidence are rejected. Caller-supplied identity/credential fields are forbidden. Freshness is rechecked before dispatch. Credentials remain inside encrypted gateway evidence/commands; no new external event or log exposes them.

These dialects are not selected automatically in the UI or used as retries. Each physical comparison requires a fresh snapshot. The modern comparison is attempted first, then the operator must report the actual native mode before the separately authorized legacy comparison is sent. No count, dates, privilege downgrade, default card or default schedule is introduced by either comparison. Existing normal expiration commands are unchanged.

The comparison support was deployed on 29 October after 52 Laravel workflow tests (565 assertions), the Go suite with PostgreSQL race checks, vet and build passed. The first modern full-record reset was acknowledged with Return=0 and returned a fresh user record. An internal comparison of encrypted before/after evidence confirmed unchanged Name, Pri, Passwd, Card, Grp, TZ, Verify and ViceCard. Mode and count remained absent from the response; the operator confirmed the rule remained Entries with count 2, so the modern comparison failed mode acceptance. A separately authorized legacy DATA USER full-record comparison was then sent from a new targeted snapshot. It also returned Return=0; an internal before/after comparison confirmed unchanged Name, Pri, Passwd, Card, Grp, TZ, Verify and ViceCard. Its response still omitted mode/count; the operator confirmed that the legacy comparison also left Entries selected with count 2. Both full-record comparisons failed native-mode acceptance. No comparison dialect is promoted to default or retried automatically; Return=0 and unchanged identity fields do not establish an expiration reset.
